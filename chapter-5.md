# Chapter 5

## Introduction <a href="#introduction" id="introduction"></a>

Ethereum is a blockchain platform that emerged in response to a major limitation of the Bitcoin platform. While Bitcoin played a pioneering role in creating a viable digital currency, it lacked the ability to be programmed to accommodate real world transactions. It was able to accommodate the transfer of bitcoins from one person to another with the help of a simple programming language but that programming language was limited.

Bitcoin makes use of a programming language called Script, which makes use of the notion of stacking the operations on top of each other and working on the top ones. It is a very old programming language -- from the 1960s -- and is also very simple. It requires very little processing power and cannot do the things that modern programming languages do. Consequently, Script is said to be Turing incomplete — a Turing complete language can perform any computation. Because of the limited things you can do with it, its choice was very suitable from a security viewpoint. If a language is complex and allows you to do many things, it offers more opportunities to creative hackers to penetrate through it and cause security lapses. The simplicity of Script affords the benefit of security.

The following section illustrates the use of Script in Bitcoin. It is a simple set of operations. More complex operations are possible. However, the complexity that is possible does not meet the requirements of most real world transactions.

## Example of limited programming on the Bitcoin platform <a href="#example-of-limited-programming-on-the-bitcoin-platform" id="example-of-limited-programming-on-the-bitcoin-platform"></a>

When bitcoins are transferred from one address to another, the holder essentially says the following in the output of a transaction:

1. x bitcoins are to be given to entity Y that is able to produce a public key whose hashing produces the same address as what I am specifying here.
2. Furthermore, that entity's public key should verify the digital signature produced by the entity.

The above requirements are in plain english. In the transaction that is transferring the bitcoins, they are put down in the form of code. This code can be seen in the [transaction in which Joe is paying Alice 0.1BTC](https://bitaps.com/7957a35fe64f80d234d76d83a2a8f1a0d8149a41d81de548f0a65a8a999f6f18) (this is a link, click on it).

After you are taken to the page displaying the transaction, click on Display scripts at the bottom.

We can make Alice’s input script compact by replacing the digital signature with \<sig> and the public key with \<PubK>. That gives us the following as Alice’s input script.

The input script provided by Alice is placed where P2PKH in Joe's script is located and the following script or code is produced:

OP\_PUSHBYTES\[72] \<sig> OP\_PUSHBYTES\[65] \<PubK> OP\_DUP OP\_HASH160 OP\_PUSHBYTES\[20] 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8 OP\_EQUALVERIFY OP\_CHECKSIG

We can substitute Alice’s address in Joe’s output script with \<PubKHash> and that gives us the following as Joe’s output script in a compact form:

OP\_PUSHBYTES\[72] \<sig> OP\_PUSHBYTES\[65] \<PubK> OP\_DUP OP\_HASH160 OP\_PUSHBYTES\[20] \<PubKHash> OP\_EQUALVERIFY OP\_CHECKSIG

This is the program that will be executed to check if Alice has the right to operate the bitcoin sent to a particular address represented as 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8.

At this point, just be clear that the ‘green’ shaded portion in the above script is what was entered by Alice and the ‘pink’ shaded portion is what was entered by Joe.

The figure shown below (which was taken from the book "[Mastering Bitcoin](https://github.com/bitcoinbook/bitcoinbook/blob/mb3dev/ch06.asciidoc)") shows how the program works. The program works by assuming a stack. Data is pushed into the stack and operations are performed on the data that happens to be at the top at that moment.

The code in the figure ignores OP\_ in front of each operation (to save space) and it also ignores OP\_PUSHBYTES, which simply is an operation to push the data that follows into a stack. The following depicts the deletion.

~~OP\_PUSHBYTES\[72]~~ \<sig> ~~OP\_PUSHBYTES~~\[65] \<PubK> \~\~OP\_\~\~DUP \~\~OP\_\~\~HASH160 \~\~OP\_\~\~PUSHBYTES\[20] \<PubKHash> \~\~OP\_\~\~EQUALVERIFY \~\~OP\_\~\~CHECKSIG

The execution of the code proceeds by using a pointer that moves through the script from the left to the right. The program begins by pushing the signature provided by Alice into the stack, which is empty to begin with (there are three figures parts in the figure, each representing a different state of the stack – look at the top of the figure). Then it pushes the public key provided by Alice (this is shown in the middle of the figure). Subsequently, it invokes the duplication operation on whatever is at the top. It is Alice's public key that is at the top. That is duplicated (this is shown at the bottom of the figure).

So far, we have achieved the following:

OP\_PUSHBYTES\[72] \<sig> OP\_PUSHBYTES\[65] \<PubK> OP\_DUP

The remaining portion is the following. It tells us what happens next.

OP\_HASH160 OP\_PUSHBYTES\[20] \<PubKHash> OP\_EQUALVERIFY OP\_CHECKSIG

The following figure takes us through the rest of the code.

In the next step, the data at the top, which is Alice's public key, is going to be hashed to produce the address from it. The following simulates that hashing. Try it.

* Copy Alice's public key, which is 0484ecc0d46f1918b30928fa0e4ed99f16a0fb4fde0735e7ade8416ab9fe423cc5412336376789d172787ec3457eee41c04f4938de5cc17b4a10fa336a8d752adf, and head to [http://gobittest.appspot.com/Address](http://gobittest.appspot.com/Address) and enter it in the space for public key. Click on Send. Focus on the result in Step 8, which is in the hex format. You see that when you take Alice’s public key via a certain hashing-based process, which includes stripping of characters, it resolves into her address, i.e., 7F9B1A7FB68D60C536C2FD8AEAA53A8F3CC025A8.

The result of hashing is now at the top of the stack. Because it is based on the hashing of the public key, it is called PubKHash.

The remaining portion is:

OP\_PUSHBYTES\[20] 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8 OP\_EQUALVERIFY OP\_CHECKSIG.

In the next step, the code pushes Alice's address provided by Joe when he directed the output to Alice (i.e., 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8) to the top of the stack. Remember that an address is based on the hashing of the public key. Consequently, we see two instances of PubKHash at the top of the stack.

The next operation is to verify if the top two items are equal. They are. They both are PubKHash, that is, hashes of Alice’s public key. The top one was provided by Joe in the form of Alice’s address in hex. The bottom one was produced when Alice’s public key was subject to a hashing-based process. Since the top two items are the same, the operation continues.

Now the only two things remaining in the stack are the public key provided by Alice and her digital signature. The next operation checks whether the signature can be verified using the public key provided by Alice and if it does, the value TRUE is pushed to the top. The Bitcoin software verifies that Alice is the legitimate owner of the bitcoins given to her by Joe and lets her proceed with directing those bitcoins to the addresses specified in the outputs of her transaction.

### Proposal to expand programming on the Bitcoin platform <a href="#proposal-to-expand-programming-on-the-bitcoin-platform" id="proposal-to-expand-programming-on-the-bitcoin-platform"></a>

The program described above was useful for enabling transfer of bitcoins from Joe to Alice. To accommodate more complex situations, a young Bitcoin enthusiast, Vitalik Buterin, proposed in October 2013 that a new layer be added on top of the Bitcoin blockchain. That would have allowed programming of more complex situations. Though his idea was seen with a lot of interest, the uptake was not as enthusiastic. In December 2013, he went on to propose a new blockchain platform, Ethereum, in a white paper. Ethereum was announced to the world in January 2014.

    &#xNAN;_**Why do we have the notion of gas on the Ethereum platform?**_

    * On the Bitcoin network, transaction fees depend mainly on the number of bytes in the transaction.
      * More inputs and outputs mean more bytes.
      * There is a fee per byte. This fluctuates with the supply and demand for processing transactions on the network.
    * On the Ethereum network, transactions can involve computation, not just data storage or transfer. Counting bytes is therefore not enough.

    _**What does gas represent?**_

    * Gas measures the amount of computational fuel consumed to execute a transaction.
    * Each operation on Ethereum (for example, executing code or storing data) consumes a specific amount of gas.
    * The more complex the computation, the more gas it consumes.
      * Same computations will consume the same amount of gas
      * Different computations will consume different amounts of gas

    _**How are gas fees calculated?**_

    * Transaction Fee = Gas Used × Gas Price (in ETH)
    * Gas Used is the total amount of computational fuel consumed by the transaction.
    * Gas Price is the cost per unit of gas and fluctuates based on supply and demand for computational resources on the network.
    * You can check the gas used for any transaction in the field labeled “Gas Limit & Usage by Txn.” Look for “Usage”. Multiply it by the gas price to find the total transaction fee.

    _**What is the difference between Gas Limit and Gas Used (or Gas Usage)?**_

    * Gas Used – the actual amount of gas consumed by the transaction.
    * Gas Limit – the maximum amount of gas you are willing to let the transaction consume.
    * If the transaction runs out of gas before completion, it fails — but you still pay for the gas already consumed.
    * Gas limit is the maximum amount of gas you (i.e., the person submitting the transaction) are willing to consume for the transaction.
* There is also a Nonce for the transaction! It refers to the sequential running number for an address. An address initiates transactions. The first transaction initiated by an address is 0, the next one is 1, and so on. We will explain the relevance later.
* You also notice Gwei. Gwei refers to Gigawei. Wei (pronounced as 'way') is the smallest unit of currency on the Ethereum platform. 1 wei is 10^-18 ETH. Giga is a billion or 10^9. Therefore, 1Gwei is 10^9 wei, which is the same as 10^-9 ETH. Gwei is pronounced as 'gway'.

### Second hands-on exercise: The computing side of Ethereum <a href="#second-hands-on-exercise-the-computing-side-of-ethereum" id="second-hands-on-exercise-the-computing-side-of-ethereum"></a>

Ethereum was not primarily designed to compete with the cryptocurrency of the Bitcoin network. In other words, ether was not created to compete with bitcoin. Ether was created to enable payment for computing on the Ethereum platform. Creating a decentralized computer that enables censor-free computing the way Bitcoin enables censor-free cryptocurrency is the chief goal of Ethereum. Computing on the Ethereum platform is enabled with what are called smart contracts. Smart contracts are probably not the best term to describe the programs on the Ethereum platform but that is the term that has buzz attached to it. We will go with that.

We will build a simple contract. This contract will act as a faucet for test ether. Anyone requesting test ether from it will be provided with test ether (from here on, we will refer to test ether as ether unless there is a special need for us to distinguish it from real ether).

#### Deploy the contract on the Ethereum testnet blockchain <a href="#deploy-the-contract-on-the-ethereum-testnet-blockchain" id="deploy-the-contract-on-the-ethereum-testnet-blockchain"></a>

You have to now deploy this contract on the Sepolia test blockchain. What it means is that your contract will be placed on an Ethereum address. That requires a special transaction.

| Exercise: Deploying the contract on the Ethereum platform with a special transaction MetaMask will help you create that special transaction. To pass on the work for that to MetaMask, do the following: Click on the 'Deploy and run transactions' icon. This is just below the compile icon in the left hand bar. This brings up the 'Deploy and run transactions pane'. Select “Browser Extension” under ‘ENVIRONMENT” and then select ‘Injected Provider – Metamask’. This means that we are going to use an injected or embedded provider of ‘connection to the Ethereum blockchain’ called Metamask. MetaMask is an injected or an embedded provider of connection in the sense that it is injected into or embedded within our browser as an extension. MetaMask will ask you to go through a process in which you select the account that will be used (if it does not ask you explicitly, click on the MetaMask icon and you will see a relevant prompt). Use the account in which you have collected some ether beforehand. Make sure you go through the process of connecting your Remix interface to your account. Click on Deploy. Metamask will show up (if it does not, just click on its icon). Press Confirm. Give it some time. You will receive confirmation that your contract has been deployed (i.e., registered). In Remix, you will see a new entry under ‘Deployed Contracts’. It will say something like ‘FAUCET at 0xE5CC…..05528 (BLOCKCHAIN)”. The 0xE5CC…..05528 part is its address. This means that your contract has been placed on the Ethereum platform. It has become an immutable part of the platform. Since it is immutable, you cannot make even the slightest change to the contract! How can anyone access your contract? For anyone to be able to engage with your contract, they will need to know its address or account on the Ethereum platform. They will also need to know additional details. We will cover that later. | Exercise: Withdraw from the contract Go to the Remix IDE. Make sure you can see that the contract is available under “Deployed Contracts”. If not, then the best way forward would be to compile the contract again (see instructions for that earlier). Then click on the icon to deploy the contract. Change the environment to Browser extension/Injected Provider - MetaMask. Then copy your contract’s address in the box to the right of “At Address” and hit ENTER. Your deployed contract will appear. Click on the icon for the “>” sign at the left of the deployed contract. An area where you can interact with the contract will show up. You will see buttons for “withdraw” and “counter”. This will bring up MetaMask (if it does not, then click on the MetaMask icon). MetaMask creates a transaction that will trigger the withdraw function. Remember that anything within a contract has to be triggered from outside. A contract cannot initiate anything on its own. We need a transaction from outside the contract to trigger the ‘withdraw’ function. That is just like our previous transaction, which triggered the function to receive 0.01 ether into the contract. MetaMask is helping us create that transaction from our account (represented as Account 1 in the MetaMask interface) to the contract account (e.g., 0xE5CCf8c2C32da01eC7114A6Ec103d31d3e805528). Confirm the transaction. Go back to your contract address to view what has happened. You may have to wait for a few seconds before you see the result. Check out the balance. It should be lower since 0.001 ether was withdrawn. What have you learned about contracts by this point? |
