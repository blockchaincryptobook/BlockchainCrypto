## Contract accounts versus externally owned accounts <a href="#contract-accounts-versus-externally-owned-accounts" id="contract-accounts-versus-externally-owned-accounts"></a>

Now let us unpack what makes the account you created with MetaMask different from the account that was created when you deployed your contract. The account that we created through MetaMask is meant for conducting transactions and is referred to as an externally owned account, or EOA. An EOA has a private key associated with it, and whoever possesses that private key controls the account and determines how it is used. Because ownership is determined by control of a private key, the account is said to be externally owned.

When you deployed the contract, it also received an address on the Ethereum network, but unlike an EOA, it does not have a private key associated with it. This means that no individual controls the contract in the way an EOA is controlled. A contract is instead considered to be owned by its logic, because its behavior is entirely dictated by the code that defines it. Whenever the contract must perform an action, it follows the logic written within it, and no external party can override that logic through private-key control.

The following diagram captures the distinction between these two forms of ownership.

<figure><img src=".gitbook/assets/image (1).png" alt=""><figcaption></figcaption></figure>

There is also an important difference between EOAs and contract accounts that the diagram does not explicitly display. This difference concerns who can initiate transactions. An EOA can initiate transactions on its own, while a contract account cannot. This follows naturally from the issue of ownership. Transactions require spending gas, and someone must decide when and whether to spend that gas. For EOAs, the private-key holder makes that decision. For a contract account, there is no such owner, so it cannot initiate transactions independently.

To execute the code inside a contract and cause it to take action, an EOA must initiate a transaction. An EOA can trigger contract execution directly, as when we sent funds to a faucet or withdrew funds from it. An EOA can also cause a contract to execute indirectly by interacting with another contract, which in turn sends a message to the first one, prompting it to run its code. Although we have not yet explored an example of this indirect approach, it is important to understand that the possibility exists and that the process always begins with an EOA.

## Account based model in Ethereum <a href="#account-based-model-in-ethereum" id="account-based-model-in-ethereum"></a>

Both Bitcoin and Ethereum rely on what are known as stateful models. A stateful model is one that tracks every state of a system along with the transitions that move the system from one state to the next. You can think of it as someone recording your daily condition—such as weight or blood pressure—while also documenting everything you did throughout the day that led from yesterday’s state to today’s. These models are especially useful because they allow verification, auditing, and learning; by examining the recorded states and transitions, one can understand what happened and why.

Although both platforms use stateful models, the specific models they employ differ. Bitcoin uses the UTXO model, while Ethereum uses the account model.

### Bitcoin's UTXO model <a href="#bitcoins-utxo-model" id="bitcoins-utxo-model"></a>

The following figure depicts Bitcoin’s UTXO model.

| <div><figure><img src=".gitbook/assets/image (4).png" alt=""><figcaption></figcaption></figure></div> |
| ----------------------------------------------------------------------------------------------------- |

In Bitcoin, the unspent transaction outputs—UTXOs—represent the state of the platform at any given time and are stored in a database. Transactions move the system from one state to another by consuming certain UTXOs and creating new ones. These transactions are added to blocks, and blocks are chained together to form the blockchain. Because an entity may have multiple UTXOs, determining its total balance requires summing all of them, much like counting the cash in a physical wallet where your total amount depends on the individual bills and coins you hold.

### Ethereum's account model <a href="#ethereums-account-model" id="ethereums-account-model"></a>

Ethereum organizes its state differently. The following figure illustrates the account-based structure used in Ethereum.

| <div><figure><img src=".gitbook/assets/image (5).png" alt=""><figcaption></figcaption></figure></div> |
| ----------------------------------------------------------------------------------------------------- |

Every account on Ethereum—whether externally owned or a contract account—has a balance, similar to a balance in a conventional bank account. This balance represents a portion of the account’s state and is stored in a dedicated state database.

For contract accounts, the state consists of two additional components. The first is `stateOfVariables`, which summarizes the values of all variables defined in the contract at any given time. For example, in the Faucet contract we used earlier, the variable `counter` represents part of the contract's state. More complex contracts may include many such variables. The second component is the `codeHash`, which is the hash of the contract’s code and ensures tamper resistance. Both `stateOfVariables` and `codeHash` are stored in the state database.

There is also another important element of an account’s state: the nonce. We will discuss the nonce later. For EOAs, however, `stateOfVariables` and `codeHash` are empty since externally owned accounts have no internal variables or code.

Transactions are the mechanism by which state changes occur on Ethereum. They alter account balances, modify contract state, deploy new contracts, or trigger functions within existing contracts. The types of transactions that update the state include the following (see source: https://web.archive.org/web/20230208040952/https://dzone.com/articles/ethereum-yellow-paper-walkthrough-27):

* Transactions that transfer value between EOAs, such as when the sender’s balance decreases and the receiver’s balance increases.\
  The illustration below shows a simple transfer of value (also available [here](https://docs.google.com/presentation/d/1Dpk8irqoYqOqMPTBBIt9GRGflpnltRf0O0a6VZNoU-g/edit?usp=sharing)).

<figure><img src=".gitbook/assets/image (11).png" alt=""><figcaption></figcaption></figure>

\
&#x20;      Our own example of donating 0.01 ether from one account to another fits into this category.

* Transactions that deploy smart contracts, such as the one we used to deploy the Faucet contract and create its contract account.
* Transactions that invoke functions within smart contracts by sending a message call.\
  For instance, when we funded the Faucet contract, we triggered the `receive` function with a transaction that transferred 0.01 ether into it. Similarly, when we withdrew 0.001 ether from the Faucet, the transaction we initiated called its `withdraw` function.

All transaction details—including the type of action being performed—are recorded in the transaction database. The results of those transactions (whether successful or not), along with metadata such as gas used and logs of internal operations, are stored in the receipt database.

## The databases in Ethereum <a href="#the-databases-in-ethereum" id="the-databases-in-ethereum"></a>

We referred to different databases where information about the states and transactions is stored. Technically, a database on the Ethereum platform is referred to as a trie. The following shows the tries more clearly along with their relationship with the Ethereum blockchain (the diagram is also available [here](https://docs.google.com/presentation/d/17j6y4ndhfbhD9OhZzAk6hDQlMKrqLqh7UPywtplZz_E/edit?usp=sharing)).

<figure><img src=".gitbook/assets/image (12).png" alt=""><figcaption></figcaption></figure>

There are two databases that store the state information. One of them is the state trie and the other is the account storage trie. The account storage trie is relevant only for contracts and it stores (a) the values of the variables in the contract, and (b) the code of the contract. A Merkle hash of the values of all variables in a contract account and the hash of the contract code are stored for any account in the state trie.

Also, the Ethereum platform uses Merkle Patricia trees as opposed to Merkle trees. But we don’t need to get into that. For our purposes, in order to keep things simpler, we will see the trees used on the Ethereum platform as Merkle trees.

So, what is the purpose of nonce on the Ethereum platform?

It keeps a count of the transactions of an account. When a verifier receives any transaction initiated by an EOA, the verifier checks the nonce. The nonce should be 1 higher than the highest nonce in the world state trie/database for that EOA. We prevent a replay attack in this way.

Even contract accounts have a nonce. In that case, the nonce keeps track of the number of contracts created by a contract.

* The faucet contract we deployed does not have the functionality to create another contract. Hence, its nonce is always 0.

## Ethereum Changes <a href="#ethereum-changes" id="ethereum-changes"></a>

The Ethereum platform continues to evolve, and many improvements have been introduced over time. Earlier, the community used the term “Ethereum 2.0” to distinguish newer developments from the original system, but that terminology has since been phased out. Instead, ongoing upgrades are now described in terms of specific changes. Two of the most significant developments are the transition from proof of work to proof of stake and the emergence of Layer 2 (L2) solutions.

### Transition to proof of stake <a href="#transition-to-proof-of-stake" id="transition-to-proof-of-stake"></a>

Ethereum’s transition to proof of stake, known as _The Merge_, took place in September 2022 and represented one of the most substantial shifts in the platform’s history. During this event, the original proof-of-work blockchain and the parallel proof-of-stake blockchain were combined into a single chain. Proof of stake replaced mining with a validator-based system.

See [video](https://youtu.be/x83EVUZ_EWo) on proof of stake.

Under proof of stake, nodes are selected to validate the network based on the amount of ether they have staked, along with an element of randomness to prevent centralization. One validator is chosen to assemble transactions into a block and propose it, while others attest to its correctness. All of these participating nodes are considered validators. With each new block, a different validator may be chosen to propose, while the rest provide attestations.

Validators who fail to perform their duties or who behave dishonestly risk losing a portion of their staked ether. The design encourages honest participation while discouraging malicious behavior.

The following description from the official documentation summarizes the validator roles and the anti-collusion structure:\
— If a validator is not selected to propose a block, it must attest to another validator’s proposed block.\
— Each block requires at least 128 validator attestations, forming what is called a _committee_.\
— Each committee works within a fixed time window, or _slot_, and only one block can be created per slot.\
— A collection of 32 slots forms an _epoch_. After each epoch, the committee is reshuffled to prevent coordinated manipulation.

This transition promised several benefits: faster block production due to the removal of computational work, dramatically reduced energy consumption because no mining hardware is required, and a more decentralized network, as anyone with staked ether can participate as a validator. The energy savings did materialize—estimated around 99.95%—while gains in throughput and security, though present, were modest. Future upgrades aim to address these limitations more substantially.

Overall, The Merge marked a transformative moment for Ethereum. It dramatically improved environmental impact and created a foundation for future scalability upgrades, including sharding and Layer 2 expansion.

### Development of Layer 2 (L2) solutions <a href="#development-of-layer-2-l2-solutions" id="development-of-layer-2-l2-solutions"></a>

Early plans to scale Ethereum focused heavily on sharding, a method that divides a blockchain into multiple smaller chains to process transactions in parallel. The vision involved splitting Ethereum into 64 shard chains, with the current chain becoming just one of them. Transactions would be distributed across shards, greatly increasing throughput. A beacon chain, launched in 2020, was designed to coordinate the work of these shards. See [video](https://www.youtube.com/watch?v=SZpjvWMfgDA) on sharding.

As Ethereum’s roadmap evolved, the role of sharding shifted. Instead of each shard executing its own smart contracts, future shards will primarily function as data-availability layers. This change aligns with the rise of Layer 2 (L2) solutions, which now form the core of Ethereum’s scaling strategy.

Layer 2 networks execute transactions off-chain, reducing the load on Ethereum’s main chain (Layer 1). They periodically post compressed or summarized transaction data back to Layer 1, relying on it for final settlement and security. This structure significantly increases transaction throughput, lowers fees, and supports the growing ecosystem of decentralized applications.

By relying on L2 networks for computation and execution while using future shards for efficient data availability, Ethereum can scale without sacrificing decentralization or security.

See [video](https://youtu.be/9pJjtEeq-N4?si=zgJxy8ZZT7B5R4Uj) on why L2 is needed and the different L2 solutions.
