# Preventing Double Spending on the Bitcoin Platform, Part 1

## Introduction <a href="#introduction" id="introduction"></a>

We have already covered how to establish that Alice—or anyone, for that matter—is the rightful owner of the bitcoins she is attempting to spend. However, verifying ownership alone is not sufficient for the viability of a digital currency. A practical and secure system must also prevent double spending. This chapter turns to that second essential requirement. Without safeguards against double spending, a user could reuse the same bitcoins multiple times, undermining the entire system. Understanding how Bitcoin prevents such behavior is crucial for appreciating why it works as a digital currency.

## Preventing double spending <a href="#preventing-double-spending" id="preventing-double-spending"></a>

In the previous class notes, we examined a [transaction](https://www.blockchain.com/btc/tx/0627052b6f28912f2703066a912ea577f2ce4da4caa5a5fbd8a57286c345c2f2) in which Alice pays Bob 0.015 BTC. She signed the input for that transaction using her private key, thereby spending the bitcoins that had previously been sent to her address. But nothing stops her—at least conceptually—from signing another transaction using the same bitcoins again and thus attempting to double spend. Since such behavior cannot be allowed, we need robust mechanisms to prevent it. To understand what is required, we begin by examining one possible method for achieving this goal.

### A possible method: Assigning serial numbers to satoshis and keeping track of them <a href="#a-possible-method-assigning-serial-numbers-to-satoshis-and-keeping-track-of-them" id="a-possible-method-assigning-serial-numbers-to-satoshis-and-keeping-track-of-them"></a>

One idea is to assign serial numbers to satoshis, the smallest unit of bitcoin, and then maintain a record of their ownership. In this approach, a centralized database would store each satoshi’s serial number along with the address of its owner. Only the legitimate owner of a given satoshi would be able to spend it, and whenever a satoshi changed hands, the database would update the serial number’s ownership entry. Once Alice transfers her satoshis to Bob, she could not spend them again because the database would record Bob as the new owner.

Although this method conceptually prevents double spending, it introduces a serious problem: someone must be responsible for maintaining the centralized database. Any centralized solution reintroduces the very third-party control that Bitcoin was designed to eliminate. Because a core motivation of Bitcoin is to avoid dependence on trusted intermediaries, this approach is fundamentally incompatible with its design philosophy. Thus, while assigning serial numbers clarifies the nature of the problem, it cannot be used in a decentralized system.

This thought experiment does, however, help us recognize two important insights. First, some form of record-keeping is absolutely essential—there must be a way to track who possesses which bitcoins and who has already spent them. Second, whatever record-keeping mechanism we use cannot be centralized. Bitcoin cannot rely on a single authoritative entity because centralization concentrates power and creates vulnerabilities. Any workable solution must instead rely on a distributed architecture in which many participants collectively maintain the necessary records.

### A distributed architecture to the rescue <a href="#a-distributed-architecture-to-the-rescue" id="a-distributed-architecture-to-the-rescue"></a>

To prevent double spending, Bitcoin relies on a distributed architecture that follows a clear logical process. Every node on the network stores a complete record of past transactions, with each transaction containing its own inputs and outputs. Only outputs from past transactions can serve as valid inputs to new transactions. When a new transaction is created, nodes refer to this historical record to ensure that none of the inputs are being reused. A transaction is valid only if it does not attempt to spend an output that has already been spent elsewhere.

To implement this logic, each node maintains its own copy of the blockchain, which is a chain of sequential blocks, each containing a batch of validated transactions. Because every node has a full copy of this history, the blockchain effectively functions as a distributed ledger. For Bitcoin to remain viable, the system must ensure that no one can spend transaction outputs that have already been spent. This requirement means that spending can occur only from the pool of unspent transaction outputs, commonly referred to as UTXOs.

Whenever someone attempts to spend bitcoins, the system must first verify that the inputs correspond to UTXOs. If an input does not correspond to an unspent transaction output, the transaction is rejected. The concept becomes clearer when examining the diagram that shows how different transactions branch out from a single earlier transaction, highlighting which outputs remain unspent. UTXOs are shown in green, indicating that they have not yet been used as inputs in any subsequent transactions. A larger version of this diagram is available [here](https://docs.google.com/presentation/u/0/d/1rpptMA9eFQsahzTHlz0UUsRv0Bp44ityF-vKrVvZLY8/edit).

While checking every past transaction would theoretically allow us to determine whether an output remains unspent, doing so repeatedly would be inefficient. To speed up verification, each node also maintains a separate database of UTXOs. Whenever someone receives bitcoins in a transaction, the output is added to the UTXO database. When that output is later spent, it is removed from the database. Just like the blockchain, this UTXO database exists independently on every node. A transaction proceeds only if each of its inputs matches an entry in the UTXO set; otherwise, it is rejected.

### Absence of totals <a href="#absence-of-totals" id="absence-of-totals"></a>

There are no totals—such as total received, total sent, or total remaining (bitcoin balance)—stored anywhere on the Bitcoin network. Maintaining such totals would require an “accounts model” similar to what is used in traditional banking systems. Bitcoin does not follow an accounts model and does not maintain databases of account balances. Instead, it uses the UTXO model, where the only records kept on the network are unspent transaction outputs.

Any totals you see on blockchain explorer websites are computed externally by third parties using the publicly available UTXOs. For example, a bitcoin balance can be determined by adding together all UTXOs associated with an address. Alternatively, one could subtract the total sent from the total received, depending on which method is used by the platform displaying the information. Different sites may compute these totals in different ways, since the Bitcoin protocol itself does not define how to calculate them.

A common approach is to begin with zero for both total sent and total received, then examine every transaction in which an address has appeared. For each transaction, the amount sent would be incremented by the total value of inputs from that address, while the amount received would be incremented by the total value of outputs sent to that address. ### Verification and updating issues <a href="#verification-and-updating-issues" id="verification-and-updating-issues"></a>

The solution outlined earlier—distributing all transaction information across the network—still leaves important questions unanswered. Specifically, we have not yet determined **who** should be responsible for validating transactions and updating the UTXO database. It is clear that Alice cannot be trusted to do this herself, because she has a strong incentive to validate her own transactions dishonestly and to avoid updating the UTXO set so she can spend the same bitcoins again later.

A natural alternative might be to ask the receiver, Bob, to handle validation and the updating process. Bob could check whether Alice’s transaction is legitimate by confirming that she is spending unspent outputs belonging to her. If everything checks out, Bob could then accept the payment, remove the spent output from the UTXO database, and broadcast this update to the rest of the network.

However, this approach fails in the face of double spending. Alice could simultaneously send the same UTXO to Bob and to Charles. Both Bob and Charles would check their local UTXO databases, which still list the UTXO as unspent. From each of their individual perspectives, the transaction looks valid. But in reality, Alice has successfully double spent, because both receivers acted independently with incomplete global information. The system needs a more robust safeguard.

Another idea is to ask the network as a whole to validate transactions. In this model, Alice broadcasts her transaction and waits for the network to collectively determine whether it is valid. However, this approach introduces significant ambiguity. It is unrealistic to require **every** node to verify a transaction, because not all nodes are online at the same time. Restricting validation to only the nodes currently active is also problematic—some nodes may be unreachable, slow to respond, or may not receive the transaction promptly due to network delays. This raises the question of how long one should wait before deciding on a consensus.

A further complication is that we cannot reliably determine exactly how many nodes are online at any given moment, which means we cannot require validation from a specific number or percentage of nodes. Even worse, Alice could game the process by introducing numerous sock puppet nodes that falsely declare her double-spend transactions as valid. With enough fake nodes boosting her claim, she could deceive Bob and Charles into accepting conflicting transactions.

Since relying on “the network” as a broad, undefined group introduces too much uncertainty, we need a more precise method. The approach adopted by Bitcoin narrows the responsibility down dramatically: the system still relies on the network for validation, but **only one entity** ultimately needs to confirm that the transaction is valid and update the UTXO database. This eliminates ambiguity about how many nodes must participate.

But making the system depend on a single validating entity presents a new vulnerability: Alice could create just one sock puppet to approve her fraudulent transactions. To prevent this, Bitcoin introduces a mechanism that makes it extremely costly and impractical for Alice (or anyone else) to cheat by impersonating this single validator.

The solution is **proof of work**, a system designed to make cheating computationally expensive and therefore unattractive. Proof of work shifts the structure of validation so that pretending to be the validating entity requires a massive expenditure of resources, making double spending vastly more difficult.

### Introducing proof of work <a href="#introducing-proof-of-work" id="introducing-proof-of-work"></a>

To prevent dishonest behavior such as double spending, Bitcoin introduces an intentional expense into the verification and updating process. The idea is to make the act of validating transactions computationally intensive and unpredictable so that attempting to cheat the system becomes prohibitively costly. Any node that wishes to participate in this process must therefore have access to significant computing power, and because the task is non-deterministic, the time required to complete it can vary widely, adding to the overall expense. By making this work costly, the system discourages bad actors from trying to manipulate the process.

However, this expense also discourages honest participants from contributing resources to the network. To counteract this effect, Bitcoin offers rewards in the form of newly created bitcoins to those who successfully perform the verification and updating work. These rewards are designed to attract well-intentioned participants. At the same time, they align incentives for potential attackers: someone who attempts to undermine the system risks devaluing the bitcoins they already possess, making dishonesty economically self-defeating. The reward structure, therefore, aims to motivate honest behavior while dissuading malicious actors.

This computationally demanding process is referred to as performing “work,” and a node that successfully completes it provides what is called “proof of work.” Because the reward can be substantial, many nodes on the network compete to validate and update transactions. The process begins when a node gathers a group of already verified transactions into a block. The verification of individual transactions is not difficult: the node simply checks that the inputs come from the UTXO database, confirms ownership by validating the digital signature, and hashes the public key provided by the sender to verify that it matches the originating address.

After collecting a valid set of transactions, the node works to solve a mathematical puzzle derived from the contents of the block. This puzzle can only be solved through trial and error. When a node eventually finds a solution, it broadcasts both the block and the solution to the network. Other nodes then validate the transactions and verify the solution. While the puzzle is hard to solve, checking the solution is easy—much like how breaking encryption is difficult, yet decrypting becomes straightforward once the correct key is found. If the block is valid, each node adds it to its existing chain of previously verified blocks.

The node that finds the solution first receives a reward. Under the Bitcoin protocol, the reward is currently 3.125 bitcoins. This block reward began at 50 bitcoins and is programmed to halve every 210,000 blocks, which occurs roughly every four years. The most recent halving took place on April 20, 2024 (UTC).

The process of validating transactions and earning rewards is known as mining, and it is a complex and richly studied topic. A useful introduction to several mining concepts can be found in the video linked in the text. Because miners solve their puzzles independently using different sets of transactions, no two nodes solve exactly the same problem. Each miner’s puzzle differs because the block they assemble is shaped by the specific transactions they receive, the order in which they receive them, and their individual criteria for which transactions to include.

Although the puzzles differ, their overall structure is the same across all miners, meaning that the time required to find a solution follows a predictable probability distribution. The network continuously monitors how long solutions take and adjusts the puzzle’s difficulty every 2016 blocks—approximately every two weeks—so that a new block is added roughly every ten minutes on average.

### Updating after showing proof of work <a href="#updating-after-showing-proof-of-work" id="updating-after-showing-proof-of-work"></a>

Once a participant on the network—say, Danielle—verifies all the transactions in her block and successfully solves the associated mathematical puzzle, she proceeds to update the blockchain. First, she appends the new block to her own local copy of the blockchain. After doing so, she broadcasts the newly constructed block to the rest of the network so that other nodes can update their own chains accordingly.

However, this leads to an important question: why should anyone believe Danielle’s block? For all we know, she could be acting as Alice’s sock puppet. To resolve such doubts, Danielle includes additional information in the block she transmits. Along with the transactions she has verified, she provides the solution to the proof-of-work puzzle as well as a hash computed from the previous block in her chain. Both of these elements play a critical role in enabling others to validate her work.

When other nodes receive Danielle’s block, they perform several checks. They verify that the puzzle solution is correct—an operation that is computationally simple even though finding the solution was difficult. They also independently validate the transactions in the block, which is relatively quick because they only need to verify authenticity and ensure that the inputs correspond to unspent outputs. In addition, they compare their own computation of the previous block’s hash with the hash Danielle included. If the two match, it confirms that Danielle’s block is built on the same chain they recognize. If the hash differs, it signals that her block is tied to an alternate chain that may not be valid. Once these checks succeed, they can safely update their blockchains.

At this point, Bob can accept Alice’s payment because the transaction has been verified by a neutral party following the network’s protocol. Danielle’s successful puzzle solution and the block she broadcasts demonstrate that she has acted according to the rules of the system. Bob can therefore trust her verification rather than relying solely on Alice’s claim.

Up to this point, the discussion has assumed that every node always has the same copy of the blockchain. In reality, however, multiple versions of the blockchain may circulate at the same time. This possibility arises because transactions are constantly being broadcast, nodes receive different subsets of them at different times, and many miners may simultaneously work on verifying different collections of transactions. It is entirely possible for two or more miners to complete blocks around the same time, which results in multiple competing blockchains—each valid from the point of view of the miner who created it.

Since these versions of the blockchain may differ, the network needs a way to manage this diversity and converge on a single chain. Otherwise, inconsistencies would arise in the record of unspent transaction outputs. For instance, an output considered unspent on one chain might be marked as spent on another. This creates an opportunity for double spending, which the system cannot tolerate.

To ensure consistency, Bitcoin relies on the length of the blockchain, measured by the number of blocks it contains. Consider a simple case with only two miners, Danielle and Emily, who initially share the same blockchain. Both begin working on new blocks, but because they have received different sets of transactions, they will construct different candidate blocks. If Emily finds the solution first, she appends her block to her chain and broadcasts it. Her chain instantly becomes longer than Danielle’s. As soon as Danielle and the rest of the network learn that Emily’s chain is longer, they abandon their own incomplete chains and begin working from Emily’s longer one.

Transactions from Danielle’s abandoned block may or may not reappear. Some of them may already have reached Emily and may therefore be included in her block. Others that have not yet reached Emily will eventually be processed by the network. It is also possible that Emily ignored some transactions because they did not satisfy her transaction-fee criteria. In any case, the network realigns itself around the longest chain.

Yet even this does not guarantee immediate synchronization. Danielle might not receive Emily’s block until Emily has already mined two new blocks, and Danielle might also have made progress on her own chain. This means their blockchains could temporarily differ by multiple blocks, and the UTXO databases on their respective nodes may also be temporarily inconsistent.

Bitcoin resolves this by defining when a transaction should be considered final. A transaction is not regarded as confirmed until its block is part of the longest chain and at least five additional blocks follow it. When these conditions are met, the transaction is said to have six confirmations. The diagram below illustrates this convergence process (a larger version can be found at the provided link).

Requiring six confirmations allows enough time—typically about sixty minutes—for the network to reach consensus. If any issues existed with the transactions in that block, they would almost certainly be detected within this window. Once the block has six confirmations, the probability that a conflicting, longer blockchain will appear is extremely small. For instance, if Alice controlled 10% of the network’s mining power, her chance of successfully reversing a transaction by exploiting competing blockchains would be only 0.1%.

### Are we able to prevent double spending? <a href="#are-we-able-to-prevent-double-spending" id="are-we-able-to-prevent-double-spending"></a>

We now examine whether Alice can still succeed in double spending under the Bitcoin protocol.

Suppose Alice currently has the longest blockchain and is mining the next block. In this new block, she could include _two_ transactions that both attempt to spend the same 0.015 BTC—one paying Bob and one paying Charlie. She then attempts to solve the proof-of-work puzzle herself. If she (or her sock puppets) controls substantial computational power, she may solve the puzzle faster than others and successfully mine the block containing both transactions, even though at least one of them must be invalid.

Once she finds the solution, she appends the block to her chain and broadcasts it to the rest of the network.

When other nodes receive her block, they proceed as usual:

* They verify her proof of work.
* They independently validate the transactions.
* They discover that the same 0.015 BTC is spent twice—once to Bob and again to Charlie.
* They cannot validate the second transaction.
* Therefore, the block is rejected.
* Since no one else accepts her chain, Alice’s blockchain remains short. Other miners continue building on a different chain, which grows longer and becomes the accepted chain.

Alice may try a different strategy. Instead of putting both double-spend transactions in the _same_ block, she may create two _different_ blocks, each spending the same 0.015 BTC, and broadcast them to different subsets of the network.

Because of communication delays:

* Subset A may accept the “Bob payment” block.
* Subset B may accept the “Charlie payment” block.
* Both subsets temporarily believe their block is valid and begin mining atop it.
* Eventually, these competing chains propagate across the network.
* Only _one_ of them will survive: the chain that becomes longer first.
* At most one payment (Bob’s or Charlie’s) will be confirmed—never both.

Thus, Bitcoin’s longest-chain rule prevents Alice from successfully spending the same coins twice in competing versions of the chain.

Alice could attempt an even more sophisticated attack. She could:

1. Pay Charlie 0.015 BTC.
2. Wait until the transaction receives **6 confirmations** (meaning it is safely embedded under 5 additional blocks).
3. Then secretly build an alternate chain in which:
   * The transaction paying Charlie never happened.
   * The 0.015 BTC is instead used to pay herself (or another identity she controls).

This is known as attempting a **blockchain fork**, where Alice tries to overwrite history by producing a longer chain than the honest one.

However, this strategy requires _extraordinary_ resources. In order to replace a transaction that has six confirmations, Alice must mine an alternate chain that overtakes the honest network’s chain. That requires controlling _more hashing power than the entire rest of the network combined_.

This is the notorious **51% attack**:

* If Alice has over 50% of total computational power, she can outpace the rest of the network.
* If she has less than 50%, the probability she eventually catches up declines exponentially.
* At present, no entity has anywhere near that level of control.

This is why confirmations matter: each additional block dramatically reduces the probability of a successful rewrite of history.
